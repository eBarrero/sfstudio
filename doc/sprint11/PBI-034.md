# PBI-034: Estabilizar SELECT y el contrato del editor de campos

- Estado: Implementada
- Prioridad: Must
- Tamaño relativo: L
- Dependencias: PBI-017 y PBI-032.
- Origen: [revisión de FieldDialog](../REVISION_FIELD_DIALOG.md), hallazgos 2, 5, 6, 7, 8 y 12.

## Historia de usuario

Como usuario, quiero seleccionar y deseleccionar expresiones de un campo sin perder otras expresiones ni confundir el bloque SOQL al navegar entre objetos.

## Alcance

1. Definir un contexto tipado del editor con la conexión (`OrgKey`), el bloque `SELECT` propietario, la ruta de relación y el campo API. No usar solo el índice local como identidad estable de una selección.
2. Cambiar el alta y la baja de SELECT para identificar una expresión por bloque, ruta de campo y función. Desmarcar una función no elimina otras del mismo campo. Evitar duplicados al volver a marcar la misma expresión.
3. Calcular el estado seleccionado desde `queryState` con un valor inicial seguro; abrir SELECT después de navegar a `RELETED` o `SUBQUERY` no debe depender de un mapa temporal vacío ni producir una excepción.
4. Validar agregados y `GROUP BY` en el bloque propietario, no contra la primera selección de la raíz. Mantener las restricciones ya soportadas por el AST.
5. Definir capacidades independientes para SELECT, WHERE y ORDER BY por tipo de campo. El diálogo no oculta las tres tareas por una sola bandera. Toda función ofrecida debe ser aceptada por el validador y el renderer; retirar o completar `convertTimezone(%1)` y las demás opciones incompatibles con el subconjunto SOQL actual.
6. Derivar opciones y estado visual de las props actuales, sin efectos con dependencias vacías ni copias locales que puedan quedar desfasadas al cambiar el campo.
7. Usar acciones compartidas para las entradas de interfaz; los componentes no mutan el árbol ni componen la SOQL.

## Criterios de aceptación

- Seleccionar dos funciones del mismo campo y quitar una conserva la otra tanto en la UI como en `queryState` y la SOQL.
- La selección de un campo en la raíz, una subconsulta y un objeto `RELETED` mantiene rutas y bloques correctos; un índice local igual en dos objetos no mezcla sus estados.
- El diálogo abre SELECT sin fallo inmediatamente después de navegar a una relación padre o hija.
- Una combinación de agregado y campo simple se acepta o rechaza conforme a las reglas del bloque que se está editando, con un error útil y sin cambio parcial del estado.
- Cada opción visible de SELECT genera un AST válido. Un tipo sin funciones SELECT admitidas muestra un estado explicativo y conserva las otras tareas disponibles.
- Los textos nuevos o modificados, incluidos errores y nombres accesibles, están en inglés correcto.

## Pruebas y documentación

- Pruebas de estado y componente para múltiples funciones del mismo campo, selección repetida, navegación raíz/hija/padre, mapa vacío y cambio de campo con el diálogo montado.
- Pruebas del contrato de capacidades frente a las funciones admitidas por el AST y del comportamiento de agregados por bloque.
- Actualizar `doc/SOQL_SOPORTADO.md` si se retira o añade una función visible.

## Evidencia de cierre

- `fieldEditorContext` registra conexión, bloque, ruta y campo; la selección visible se calcula desde `queryState`. La navegación a padre e hijo crea un mapa seguro incluso antes de cargar toda la metadata.
- SELECT distingue expresiones por campo API y función dentro de cada elemento; las reglas de agregación usan el bloque propietario y rechazan cambios incompletos. La interfaz oculta temporalmente el control ORDER BY sin efecto hasta PBI-036.
- Se retiró `convertTimezone(%1)` del catálogo visible y se documentó el subconjunto vigente.
