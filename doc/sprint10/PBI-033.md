# PBI-033: Gestionar LIMIT por bloque SOQL desde «Where Clause»

- Estado: Planificada
- Prioridad: Must
- Tamaño relativo: M
- Dependencias: PBI-017 (modelo SOQL), PBI-031 (pestañas del panel de objeto), PBI-032 (bloques `ROOT` y `SUBQUERY`).

## Historia de usuario

Como usuario que construye una consulta SOQL, quiero elegir el límite de cada bloque `SELECT` desde la pestaña «Where Clause», para controlar cuántos registros solicita la raíz y cuántos devuelve cada subconsulta hija.

## Estado actual

`QueryState` no tiene un `limit` global: el valor vive en cada elemento `ROOT` o `SUBQUERY` de `queryState.queryElemnts`. `RELETED` es solo navegación y no genera un bloque `SELECT` ni un `LIMIT` propio. Al crear una consulta, la raíz empieza con `LIMIT 50` y cada subconsulta hija con `LIMIT 1`. El AST admite omitir `LIMIT` o usar un entero de 1 a 2000. La API aplica además un límite de ejecución independiente, con un máximo de 2000 registros y paginación controlada.

## Comportamiento propuesto

En `app/src/components/organisms/sObjectPanel/whereClausePanel.tsx`, añadir una tabla con estas cuatro columnas:

| Object | All | 1 | Other |
| --- | --- | --- | --- |
| Nombre API del objeto del bloque | Casilla para omitir `LIMIT` | Casilla para `LIMIT 1` | Entrada numérica para otro límite |

- Mostrar una fila por bloque `ROOT` o `SUBQUERY`, en el orden de `queryState.queryElemnts`. Excluir `RELETED`, porque sus campos pertenecen al `SELECT` de un bloque ancestro.
- La opción `All` elimina la cláusula `LIMIT` de ese bloque en la SOQL generada. **No elimina** el límite de seguridad de la API ni implica descarga ilimitada: la ejecución continúa con un máximo de 2000 registros y paginación bajo demanda. La interfaz debe explicar esta diferencia cerca de la tabla.
- La opción `1` asigna `LIMIT 1` al bloque.
- `Other` permite un entero entre 2 y 2000. Una entrada vacía, decimal, negativa, fuera de rango o no numérica muestra un error y conserva el último valor válido; no modifica la consulta ni las otras filas.
- En cada fila solo hay un modo activo. Marcar `All` o `1` desactiva el otro modo; introducir y confirmar un número válido activa `Other`. El valor visible de cada fila se deriva del estado del bloque, incluso después de navegar, guardar y cargar una consulta.
- La tabla permanece visible aunque no existan condiciones `WHERE`. El listado de condiciones y el editor de `whereLogic` actuales conservan su comportamiento.

## Diseño técnico

1. Representar la ausencia de `LIMIT` en `PrimaryQuery` y `NestedQuery` como `limit?: number`, coherente con el AST. El cambio se aplica únicamente a bloques `SELECT`.
2. Añadir una acción en `modelState` que reciba el índice del bloque y el modo o valor elegido, valide la entrada, clone el árbol y regenere `sqlState` de forma atómica. La UI no construye SOQL ni muta directamente `queryState`.
3. Mantener la validación estructural existente del AST para números de 1 a 2000. En esta UI, `Other` empieza en 2 porque `1` tiene una columna propia.
4. Revisar el límite que el frontend envía al ejecutar la consulta raíz. Hoy se solicitan 200 registros a la API: una SOQL con `LIMIT` mayor fallaría porque la API exige que el límite declarado no supere el solicitado. La acción de ejecución debe pedir un cupo coherente con la selección de la raíz, siempre acotado por 2000. Para `All`, usar el cupo seguro máximo de 2000 y conservar la paginación. El `LIMIT` de una subconsulta no determina el cupo de registros raíz.
5. Conservar el valor opcional en las definiciones SOQL guardadas y restaurarlo al cargar. Si cambia el contrato persistido, actualizar su versión; en desarrollo no se requieren migraciones.
6. Mantener sin cambios las acciones y rutas de `Show_Where`, el menú «views → Where Clause» y la pestaña. No se añade botón a la consola.

## Criterios de aceptación

- Con una consulta nueva, la tabla muestra la raíz en `Other = 50` y cada subconsulta hija con `1` seleccionado.
- La tabla contiene exactamente las columnas `Object`, `All`, `1` y `Other`, con el nombre API de cada bloque `SELECT`. No aparecen filas para nodos `RELETED`.
- Elegir `All`, `1` u `Other = N` en una fila cambia únicamente el `LIMIT` de ese bloque y actualiza inmediatamente la SOQL generada. `All` omite la cláusula del bloque.
- Las opciones de una fila son excluyentes y no alteran las demás filas. Introducir un valor inválido conserva el último estado válido y muestra un mensaje accesible.
- La tabla funciona sin condiciones `WHERE` y no altera `where`, `whereLogic`, selección de campos ni navegación.
- Una consulta con `LIMIT` raíz entre 201 y 2000 puede ejecutarse sin rechazo por desacuerdo entre el límite SOQL y el cupo enviado a la API. `All` mantiene el límite de seguridad y la paginación.
- Guardar y cargar una consulta conserva la elección de la raíz y de las subconsultas. La opción `All` sigue omitiendo `LIMIT` tras la carga.
- `Show_Where`, la opción de menú y la pestaña continúan abriendo el mismo panel mediante el mismo `ActionId`.

## Pruebas requeridas

- Unitarias de estado/AST para `All`, `1`, `Other`, independencia de bloques y rechazo atómico de valores inválidos.
- Componente para tabla, cabeceras, selección excluyente, errores accesibles, ausencia de filas `RELETED` y visualización sin condiciones `WHERE`.
- Integración de ejecución para límites raíz mayores de 200, `All`, máximo 2000 y paginación bajo demanda.
- Regresión de guardado/carga y paridad de `Show_Where`.
