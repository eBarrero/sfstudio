# PBI-042: Registrar la ruta HTTP solicitada, incluidos los 404

- Estado: Implementada.
- Prioridad: Must.
- Tamaño relativo: M.
- Dependencias: PBI-003 (logger estructurado). Independiente de PBI-039, PBI-040 y PBI-041.

## Historia de usuario

Como responsable de operar SF Studio, quiero identificar en el log qué ruta HTTP se solicitó para localizar errores de enrutamiento, especialmente cuando la ruta no existe y el servidor responde `404 NOT_FOUND`.

## Situación actual

`correlationMiddleware` registra `http.request` con `correlationId` y método, pero sin ruta. `notFoundHandler` registra `http.not_found` con esos mismos datos, por lo que no permite saber qué página o endpoint se pidió. La aplicación sirve recursos estáticos en producción y termina en el mismo manejador de rutas desconocidas.

## Criterios de aceptación

1. Cada evento `http.request` incluye una representación segura de la ruta solicitada, además de `correlationId` y método. El evento `http.not_found` incluye esa ruta segura, método, `correlationId` y estado `404`. Una petición a una ruta inexistente permite identificar la ruta cuando sus segmentos son seguros para el log.
2. No se registra la URL completa, query string, fragmento, cuerpo, cookies, cabeceras, códigos OAuth, `state`, tokens, cursores, texto SOQL, `OrgKey`, identificadores personales ni otros valores dinámicos sensibles. Para rutas conocidas se prefiere una plantilla sin parámetros; en una ruta desconocida se sanea y limita el path antes de registrarlo. Si un segmento no puede considerarse seguro, se sustituye por un marcador de redacción. No se confía solo en la redacción genérica del logger.
3. La ruta registrada sigue siendo útil para distinguir páginas o endpoints inexistentes de forma segura, por ejemplo `/api/ruta-inexistente`, y conserva el prefijo necesario para diagnosticar un 404. Se documenta el criterio de saneamiento y el nombre del campo del log.
4. La respuesta HTTP de rutas inexistentes conserva `404`, el código público `NOT_FOUND` y el `correlationId`. No se añade la ruta a la respuesta pública ni se cambia el comportamiento de los endpoints existentes.

## Pruebas y documentación

- Pruebas con logger falso para una ruta conocida y una inexistente: verificar evento, método, ruta segura, estado del 404 y correlación con la respuesta.
- Pruebas negativas con query de OAuth, cursor, SOQL, email, `OrgKey`, segmentos codificados y path muy largo: ningún dato sensible ni URL completa aparece en los logs; una ruta no segura queda redactada.
- Actualizar `doc/ARQUITECTURA.md` y `doc/GUIA_DESARROLLO.md` con el contrato y el saneamiento de los logs. Ejecutar typecheck y tests de `api` antes de marcar la PBI como implementada.

## Evidencia de cierre

- `safeRequestPath` genera una ruta corta, sin query string, con redacción de segmentos codificados, identificadores y valores sospechosos. `correlationMiddleware` registra la plantilla de rutas conocidas al finalizar la respuesta; `notFoundHandler` registra el path seguro, método, estado 404 y correlación.
- `api/test/httpRequestPath.test.js` verifica ruta conocida, endpoint y página inexistentes, respuesta 404, correlación y ausencia de valores sensibles; `api/test/correlationRequest.test.js` comprueba el evento de petición.
- Validación local: typecheck, lint y tests de `api` pasan (82 pruebas). Los tests HTTP requieren acceso a loopback.
