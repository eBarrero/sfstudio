# PBI-006: OAuth correcto para producción y sandbox

- Estado: Implementada; pendiente de validación manual con orgs controladas y en CI
- Prioridad: Must
- Tamaño relativo: L
- Dependencias: PBI-005

## Historia de usuario

Como usuario, quiero conectar cualquier org autorizada con el mismo flujo, sea producción o sandbox.

## Objetivo

Corregir selección de login host y eliminar la lógica duplicada o errónea de tecnología.

## Alcance

- Corregir reconocimiento de SF_Prod y SF_Test.
- Transportar loginHost dentro del contexto OAuth validado.
- Usar login.salesforce.com o test.salesforce.com en autorización e intercambio según contexto.
- Mantener capacidades idénticas después del login.
- Preparar configuración compatible con External Client App sin bloquear Connected Apps existentes.

## Criterios de aceptación

- El login de producción intercambia el code contra el host correcto.
- El login de sandbox usa el host de sandbox.
- Ningún host se deduce de datos manipulables del callback.
- Ambos flujos producen el mismo OrgConnection normalizado.
- Errores de Salesforce se traducen a códigos internos sin filtrar detalles sensibles.

## Pruebas requeridas

- Integración con drivers OAuth falsos para ambos hosts.
- Prueba manual controlada con una org de cada tipo.

## Fuera de alcance

- Diferenciar funcionalidades por entorno.
- Client credentials flow.

## Definition of Done

- Criterios demostrados con pruebas automatizadas o evidencia manual indicada.
- Contratos y errores públicos documentados.
- Ningún token aparece en MongoDB, respuestas o logs.

## Evidencia de implementación

- `SF_Prod` y `SF_Test` se reconocen por igualdad exacta. Los hosts canónicos se calculan antes de emitir `state`, se guardan junto al destino y se validan al consumirlo.
- El adapter Salesforce usa el mismo `loginHost` en la URL de autorización y en `jsforce.OAuth2` para intercambiar el código. `instanceUrl` y los parámetros del callback no pueden sustituirlo.
- Los dos entornos producen el mismo DTO de conexión y exponen las mismas capacidades. El host y el tipo de entorno siguen visibles en el contrato del workspace.
- Los errores del adapter se convierten en `502 SALESFORCE_AUTH_FAILED` con mensaje público fijo y `correlationId`; tecnologías o hosts inconsistentes producen `400 OAUTH_CONTEXT_INVALID`. No se registran códigos, URLs completas ni mensajes del proveedor.
- Las pruebas usan un cliente OAuth falso para comprobar ambos hosts, el contrato normalizado y la redacción del error. Las pruebas HTTP comprueban que una query manipulada no cambia el host del callback.
- `CLIENT_ID`, `CLIENT_SECRET` y el callback existente funcionan con Connected Apps y External Client Apps configuradas para Web Server Flow. La configuración que exige PKCE requiere una PBI posterior.
- La [guía de desarrollo](../GUIA_DESARROLLO.md) contiene la verificación manual pendiente con una org controlada de cada tipo. No se usaron credenciales reales en CI.
