# PBI-005: Identidad estable de organización y contratos multi-org

- Estado: Implementada; pendiente de validación en CI y con MongoDB real
- Prioridad: Must
- Tamaño relativo: L
- Dependencias: PBI-004

## Historia de usuario

Como usuario, quiero que SF Studio distinga correctamente cada organización y usuario aunque sus alias o dominios sean parecidos.

## Objetivo

Introducir OrgKey y DTOs explícitos para workspace, organización configurada y conexión activa.

## Alcance

- Definir OrgKey a partir de organizationId y userId.
- Separar alias, instanceUrl, loginHost, environmentKind y estado de conexión.
- Sustituir índices de array como identidad externa por OrgKey.
- Versionar los contratos JSON de workspace y conexión.
- Diseñar migración o invalidación segura de documentos Mongo antiguos.

## Criterios de aceptación

- Dos conexiones con alias iguales mantienen identidades distintas.
- Cambiar un alias no invalida caché ni conexión.
- Los endpoints nunca usan la posición del array como identificador persistente.
- El contrato distingue CONNECTED, REAUTH_REQUIRED, CONNECTING y ERROR.
- Los datos antiguos se migran o fuerzan a reconectar de forma controlada.

## Pruebas requeridas

- Unitarias de construcción y comparación de OrgKey.
- Contrato de serialización del workspace.
- Migración con documento anterior.

## Fuera de alcance

- Alias compartidos entre usuarios.
- Comparación de esquemas.

## Definition of Done

- Criterios demostrados con pruebas automatizadas o evidencia manual indicada.
- Contratos y errores públicos documentados.
- Ningún token aparece en MongoDB, respuestas o logs.

## Contrato y migración implementados

- `OrgKey` es `organizationId:userId`, con IDs Salesforce de 15 o 18 caracteres alfanuméricos. Es la clave del registro de conexiones, el pool, la org activa y la ruta de reautenticación.
- `GET /api/v1/workspace` devuelve JSON `{ version: 1, connections, activeOrgKey }`. Cada conexión incluye `orgKey`, `organizationId`, `userId`, `userName`, `alias`, `instanceUrl`, `loginHost`, `environmentKind` (`PRODUCTION` o `SANDBOX`) y `status` (`CONNECTED`, `REAUTH_REQUIRED`, `CONNECTING` o `ERROR`). Sin cookie devuelve un workspace vacío; una cookie inválida produce `401 SESSION_INVALID` con `correlationId`.
- `GET /api/v1/connections/:orgKey/authorize` inicia la reautenticación de una conexión del workspace. El callback comprueba que Salesforce devuelve exactamente el `OrgKey` solicitado antes de registrarla.
- Una clave mal formada devuelve `400 ORG_KEY_INVALID`; una clave válida que no pertenece al workspace devuelve `404 ORG_NOT_FOUND`. Ambos errores usan el sobre público `{ error: { code, message, correlationId } }` y no exponen datos de la conexión.
- En la primera lectura de un documento Mongo heredado, las conexiones con `dbId` y `userId` válidos se actualizan a la versión 1 y reciben `loginHost` según `tech`. Las filas sin identidad válida o duplicadas se eliminan de la lista de conexiones conocidas: no es seguro inferir su identidad desde `dbName`, alias o hostname. El usuario debe volver a conectar esas orgs. No se migran ni persisten tokens.
- Si un despliegue antiguo creó índices únicos en `connections.userName` o `connections.userId`, el repositorio los retira antes de escribir conexiones, después de verificar sus nombres, claves y unicidad. Si la cuenta de la aplicación no tiene permiso `dropIndex`, el operador debe retirarlos tras revisar `db.users.getIndexes()`. Se conserva el índice único de `sessionId` hasta una migración independiente.
- Tras reiniciar el servidor, las orgs conocidas vuelven como `REAUTH_REQUIRED`. Un alias nuevo no cambia `OrgKey` ni el estado de una conexión viva.
- Un OAuth nuevo sin cookie de workspace crea una sesión nueva incluso si el usuario Salesforce ya era conocido; nunca se reutiliza la sesión activa de otro navegador.

## Evidencia local

- Pruebas unitarias de construcción y comparación de `OrgKey`, dos conexiones con alias iguales, cambio de alias y migración de un documento anterior.
- Pruebas HTTP del workspace versionado y de la cookie; typecheck, lint y build de ambos workspaces.
- La migración con un MongoDB real y el OAuth real requieren un entorno controlado; esta PBI no afirma haberlos validado localmente.
