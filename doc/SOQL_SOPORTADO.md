# Subconjunto SOQL de la primera fase

El constructor genera únicamente `SELECT`. La raíz usa un objeto API, campos individuales o `FIELDS(ALL|CUSTOM|STANDARD)`; estos últimos ocupan toda la lista de selección. Se admiten rutas de relación padre, una subconsulta hija por relación con campos seleccionados, funciones `COUNT`, `COUNT_DISTINCT`, `SUM`, `AVG`, `MIN`, `MAX`, `FORMAT` y las funciones de fecha enumeradas en `app/src/core/soql/domain.ts`. `convertTimezone(%1)` no se ofrece porque no está admitida por el AST y el renderer. Cada expresión seleccionada se identifica por bloque, ruta de relación, campo API y función; desmarcar una función no retira las demás del mismo campo.

Las condiciones estructuradas usan comparaciones (`=`, `!=`, `<`, `<=`, `>`, `>=`, `LIKE`), conjuntos (`IN`, `NOT IN`, `INCLUDES`, `EXCLUDES`) y grupos `AND`/`OR`. Los literales se representan por tipo y se escapan al renderizar. `ORDER BY`, `GROUP BY`, `LIMIT` y `OFFSET` están disponibles; `LIMIT` y `OFFSET` aceptan enteros entre 1 y 2000, y 0 y 2000, respectivamente. Las consultas agregadas con campos sencillos exigen `GROUP BY` para esos campos. La subconsulta no admite otra subconsulta. La ruta visual puede mostrar un hijo de otro hijo para explorar su metadata, pero esa selección no genera SOQL ejecutable en esta fase.

El editor WHERE admite comparaciones de texto y número, rangos inclusivos (`>= From AND <= To`) y su complemento (`< From OR > To`), y comparaciones con `NULL`. Los booleanos se guardan como `TRUE`/`FALSE`; las picklists usan `IN`/`NOT IN` y las multipicklists `INCLUDES`/`EXCLUDES`, siempre con al menos un valor. Para fechas y fechas-hora se admiten valores ISO explícitos y los literales relativos de día, semana, mes, trimestre, año, trimestre fiscal y año fiscal enumerados en `app/src/core/soql/dateLiterals.ts`. Los literales parametrizados requieren `N` entre 1 y 999; el editor explica el período seleccionado y muestra el predicado antes de aplicarlo. Los períodos fiscales dependen del calendario fiscal de la organización conectada. Las fechas y rangos personalizados usan los modos `Date` y `Range`, no pseudoliterales SOQL. Las fechas-hora introducidas manualmente requieren UTC explícito (`YYYY-MM-DDTHH:mm:ssZ`); el editor no convierte zonas horarias implícitamente. La vista previa de cada condición se genera del mismo predicado tipado que usa la SOQL final.

Cada bloque `SELECT` (`ROOT` o `SUBQUERY`) conserva un único array `where` y una expresión `whereLogic`. Los nodos `RELETED` solo sirven para navegar y seleccionar campos; una condición creada desde ellos se añade al bloque `SELECT` propietario con una ruta de relación, por ejemplo `Account.Owner.Name`. Así, condiciones del objeto base y de sus padres pueden mezclarse en el mismo `WHERE`, mientras cada subconsulta hija mantiene su propio filtro. El contrato del campo separa `relationshipPath` (nombres de relación estables), `fieldApiName` (campo final) y `fieldIndex` (índice local transitorio). El renderer genera la ruta a partir de los dos primeros, sin utilizar `sqlString`.

`C1` referencia la primera condición del `where` de ese bloque, `C2` la segunda, etc.; el índice 0 y los índices superiores al número de condiciones son inválidos. Al añadir condiciones se genera `C1 AND C2 ...` por defecto. Si ya había una lógica personalizada, se agrupa entre paréntesis y se añade la nueva condición con `AND`. La pestaña «Where Clause» muestra una lista numerada y un editor por bloque, con las rutas cualificadas visibles. Los paréntesis deben estar equilibrados, cada grupo debe contener una expresión y los operadores deben separar dos expresiones. `AND` tiene prioridad sobre `OR` cuando no hay paréntesis. Una expresión inválida no sustituye la anterior ni altera la SOQL generada.

La tabla `Object | All | 1 | Other` de «Where Clause» gestiona `LIMIT` de cada bloque `SELECT`, incluso si no tiene condiciones. `RELETED` no tiene fila propia. `All` omite `LIMIT` en la SOQL; `1` usa `LIMIT 1`, y `Other` acepta enteros de 2 a 2000. La raíz empieza en 50 y las subconsultas hijas en 1. La API mantiene un cupo de ejecución independiente: para `All` es 2000 filas como máximo, y la paginación continúa bajo demanda. El cupo solicitado para un `LIMIT` explícito de la raíz coincide con ese valor; los límites de las subconsultas no cambian el cupo de registros raíz.

Cada bloque `SELECT` mantiene su propia lista `ORDER BY`. Un orden conserva campo API y ruta de relación relativa al bloque, dirección `ASC`/`DESC` y una política explícita `NULLS FIRST`/`NULLS LAST`. El orden del array determina la prioridad. Un campo de `RELETED` se guarda en su bloque padre; el panel «Order Clause» agrupa raíz y subconsultas, sin fila independiente para `RELETED`.

Las definiciones SOQL guardadas usan el formato 4, que permite omitir `limit` en cada bloque `SELECT` y conserva la prioridad y política de nulos de `ORDER BY`. Al cargarlas en otra organización se resuelven de nuevo las relaciones y el campo final de cada condición y orden contra la metadata de destino; las relaciones inexistentes o ambiguas y los campos ausentes impiden la carga completa. En esta fase de desarrollo no se migran las definiciones anteriores y se puede reiniciar IndexedDB.

No se implementa un parser de SOQL libre, `HAVING`, `TYPEOF`, funciones arbitrarias ni mutaciones. Una consulta inválida produce errores con código y ruta del nodo. La API valida por separado cualquier texto SOQL recibido, porque el AST del navegador no es una frontera de seguridad.
